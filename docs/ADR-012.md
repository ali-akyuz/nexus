# ADR-012: Separate Python ML Service

**Date**: 2026-08-17
**Status**: Accepted

## Context
NEXUS requires the execution of data analysis and machine learning tasks (e.g., Pandas data manipulation, scikit-learn clustering).
Our core application and job queue infrastructure is written in TypeScript (Node.js/NestJS). Running heavy CPU-bound Python workloads directly inside Node.js or attempting to rewrite ML algorithms in JavaScript is strongly discouraged for performance, ecosystem, and maintenance reasons.

## Decision
We will extract ML and data processing into a stateless **FastAPI Python Microservice** (`apps/ml-service`).
- **Node.js Worker**: Continues to own the BullMQ consumption, job state in PostgreSQL, and real-time WebSocket progress updates.
- **Python Service**: Exists solely to receive an HTTP POST request, compute the result deterministically using Pandas/scikit-learn, and stream progress events back to Node over an HTTP JSON-lines stream.

## Consequences
- **Positive**: Best-in-class ML libraries can be used natively. Node.js workers remain highly available and responsive to the queue since they only block on HTTP network requests, rather than CPU cycles.
- **Negative**: Adds a secondary language ecosystem (Python) and a new service to the local Docker Compose cluster, slightly increasing operational complexity.
- **Mitigation**: Internal service authentication (`X-Internal-Service-Key`) secures the boundary, and strict HTTP timeout limits prevent Python service outages from permanently locking Node workers.
