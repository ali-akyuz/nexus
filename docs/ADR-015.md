# ADR-015: Observability Architecture

## Context
As NEXUS scales, we need visibility into the API, BullMQ queues, worker nodes, and the ML microservice. Identifying bottlenecks, failure points, and performance regressions is impossible without a structured observability strategy.

## Decision
We will adopt **Prometheus** for metrics, **OpenTelemetry** for distributed tracing, and **Grafana** for visualization, with the following constraints:
1. **Metrics Backend**: Prometheus (Pull model).
2. **Tracing Backend**: Jaeger All-In-One (Push model, memory-backed). This is chosen as the absolute lightest way to fulfill the trace visualization requirement without introducing heavy elasticsearch or full Jaeger/Zipkin clustered architectures.
3. **Trace Propagation**: We bridge the async BullMQ gap by injecting the W3C `traceparent` context into the BullMQ job `data._traceContext` payload during `enqueue`, and extracting it using OpenTelemetry APIs within the Worker process.
4. **Dashboards**: Grafana is auto-provisioned locally to visualize the metrics and traces instantly upon `docker compose up`.

## Consequences
- **Positive**: We gain a complete picture of an operation from API HTTP Request -> Redis -> Worker -> ML Service HTTP Request.
- **Positive**: Extremely lightweight local setup (no massive Kafka or Elasticsearch clusters).
- **Negative**: Jaeger all-in-one loses traces on restart. For a production deployment, this will be swapped for an OTLP-compatible backend (like Grafana Tempo or DataDog).
