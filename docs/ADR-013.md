# ADR-013: Analytics Aggregation Strategy

**Date**: 2026-08-17
**Status**: Accepted

## Context
Phase 7 requires a Dashboard with advanced real-time time-series analytics, performance metrics, and complex filtering/pagination of historical jobs.
As data scales, analytical queries (`GROUP BY`, `date_trunc`, `AVG`) can become expensive.

## Decision
We will use native **PostgreSQL aggregation** via Prisma and Raw SQL for the initial analytics implementation.
- We deliberately **avoid** introducing Elasticsearch, ClickHouse, or Kafka at this stage to keep the architecture understandable and manageable for a portfolio-scale project.
- New B-Tree indexes (`@@index([type])`, `@@index([userId, createdAt])`, `@@index([status, createdAt])`) have been added to the `Job` model to optimize the specific filtering and aggregation patterns.
- Raw SQL (`$queryRaw`) is used strictly for time-series bucketing (`date_trunc`) and epoch math (`EXTRACT(EPOCH)`) where Prisma's ORM syntax is either too verbose or unsupported.

## Consequences
- **Positive**: No new infrastructure dependencies required. The stack remains simple (NestJS + Postgres). Indexes ensure reads are performant for hundreds of thousands of rows.
- **Negative**: If job volume scales into the tens of millions, PostgreSQL analytical queries will begin to slow down and lock transactional tables.
- **Mitigation**: Once metrics indicate slow analytical queries, we can introduce a materialized view in PostgreSQL or implement a background cron job to precompute daily metric rollups.
