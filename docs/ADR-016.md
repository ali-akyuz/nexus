# ADR-016: Production Deployment Architecture

## Context
NEXUS requires a reliable, scalable, and secure deployment mechanism that integrates with our CI/CD pipelines while maintaining environment parity across Dev, Staging, and Production.

## Decision
We will standardize on **Kubernetes** as our orchestration platform and **Helm** as our package manager, alongside **GitHub Actions** for CI/CD automation.

### Architecture
- **GitHub Actions**: 
  - `ci.yml`: Validates code through type checks, linting, and tests.
  - `docker.yml`: Builds Docker containers on version tags and pushes to GitHub Container Registry (ghcr.io) using commit SHA tags.
  - `deploy.yml`: Upgrades the Helm chart release targeting specific environments (`staging`, `production`).
- **Helm**: 
  - A unified chart `deploy/helm/nexus` orchestrates `web`, `api`, `processor`, and `ml-service` deployments.
  - Value overrides (`values-staging.yaml`, `values-prod.yaml`) manage replica counts, resource limits, and auto-scaling constraints.
  - **Database Migrations** are executed via a Helm Job annotated with `"helm.sh/hook": pre-upgrade`. This ensures the database schema is updated before the new application pods roll out.
- **Docker**:
  - `pnpm dlx prisma generate` has been integrated into the Docker builders.
  - All containers drop privileges to run as a non-root `nestjs` or `myuser` account.

## Consequences
- **Positive**: Complete deployment reproducibility across environments.
- **Positive**: Zero-downtime deployments via Kubernetes rolling updates and pre-upgrade hooks.
- **Positive**: HPA (Horizontal Pod Autoscaling) is enabled for production workloads.
- **Negative**: Adds Kubernetes complexity (requires a managed cluster like EKS/GKE and operational knowledge).
