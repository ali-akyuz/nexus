# ADR-014: Rate Limiting & Back-Pressure Strategy

**Date**: 2026-08-17
**Status**: Accepted

## Context
NEXUS requires protection against abusive traffic, queue over-saturation, and memory exhaustion from maliciously large payloads or infinite concurrent job submissions.

## Decision
We implement a multi-layered defense-in-depth strategy:
1. **API Rate Limiting**: NestJS `@nestjs/throttler` enforces global request limits (100 req/m), with strict overrides on Authentication (10 req/m) and Job Creation (20 req/m) endpoints.
2. **Queue Back-Pressure**: Before pushing a new job to BullMQ, we check the Redis `waiting` queue size. If it exceeds `MAX_QUEUE_DEPTH` (default 500), we reject with HTTP 503 (`QUEUE_OVERLOADED`).
3. **User Concurrency Limits**: We count a user's active jobs in PostgreSQL. If they have more than `MAX_CONCURRENT_JOBS_PER_USER` (default 10) in `QUEUED` or `PROCESSING` state, we reject new jobs with HTTP 429 (`CONCURRENCY_LIMIT_REACHED`).
4. **Priority Protection**: Only users with the `ADMIN` role can submit jobs with `CRITICAL` priority.
5. **Configuration Hardening**: We use `Joi` to strictly validate environment variables on boot, explicitly rejecting weak JWT secrets when `NODE_ENV=production`.

## Consequences
- **Positive**: The system naturally resists overload and degrades gracefully via well-formed HTTP codes. The queue cannot grow infinitely, preventing Redis OOM errors.
- **Negative**: Legitimate users with valid bulk workloads may hit the user concurrency limits.
- **Mitigation**: These limits are entirely configurable via Environment Variables so they can be tuned based on the deployment scale.
